# Brainstorming 阶段 — 深度设计与探索

## 阶段目标
对较复杂或模糊的需求进行多轮设计探索，输出技术方案、架构决策和可选方案的权衡分析。最终产出 `design.md`（可选补充 `proposal.md`）。

## 输入条件
- 已有活跃变更目录（已创建 `proposal.md` 或用户直接要求深度设计）
- 需求范围存在不确定点，需要 AI 主动提问和探索。

## 核心流程

### 1. 读取现有信息
- 读取 `openspec/changes/<change-name>/proposal.md`（如果存在）
- 理解 What/Why/Scope 和验收标准

### 2. 识别设计问题（必问清单）
向用户提出以下问题（根据场景选择）：

- **数据模型**：需要新增哪些实体、字段、关系？
- **API 设计**：需要哪些端点？请求/响应格式？
- **UI/UX**：界面布局、交互流程？是否需要原型？
- **技术依赖**：需要引入新的库或服务吗？
- **边界条件**：错误处理、回滚策略、并发控制？
- **可替代方案**：有没有其他实现路径？各自的 trade-off 是什么？

### 3. 生成 `design.md`
在变更目录下创建 `design.md`，结构示例：

```markdown
# Design: <变更名称>

## 概述
[来自 proposal 的 What 和 Why]

## 技术方案
### 方案 A（推荐）
- 描述
- 优点
- 缺点

### 方案 B
- 描述
- 优点
- 缺点

## 最终决策
选择方案 A，原因：……

## 详细设计
### 数据模型
[ER 图或字段列表]

### API 定义
[端点、请求/响应示例]

### UI 交互
[关键页面或流程图]

## 风险与应对
- 风险1 → 应对措施
```

### 4. 多轮探索
- 提出“是否考虑 X 场景？”、“如果数据量大怎么办？”等问题。
- 根据用户反馈更新 `design.md`。
- 直到用户表示“设计已确认”或“可以了”。

### 5. 完成提示
> “设计已定稿。请使用 `spec` 生成正式的规格和实现计划。”

## 出口条件
- `design.md` 存在且用户确认过。

## 禁止行为
- ❌ 编写任何代码或测试
- ❌ 修改 `plan.md`（本阶段尚未生成）
- ❌ 执行任何实现命令
